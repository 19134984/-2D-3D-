# Multi-GPU thermal lattice Boltzmann simulations using OpenACC and MPI

作者：Ao Xu, Bo-Tao Li  
期刊：International Journal of Heat and Mass Transfer  
年份：2022

## 主要工作

这篇论文最重要的地方，不是提出了一个全新的热格子玻尔兹曼模型，而是把一个已经成熟的热 LBM 框架，系统地搬到了多 GPU 平台上，并把这条路线中最关键的工程瓶颈逐个拆开、量化、优化。

作者研究的是 `Boussinesq` 近似下的热对流，用的是双分布函数 `DDF` 热 LBM：

- 2D 流场：`D2Q9`
- 2D 温度场：`D2Q5`
- 3D 流场：`D3Q19`
- 3D 温度场：`D3Q7`
- 流场与温度场碰撞都采用 `MRT`

从物理模型上看，这套东西并不陌生，甚至可以说是“标准配置”。真正的贡献在于，作者没有停留在“单卡能跑”，而是进一步回答了下面这几个更难、也更接近真实科研代码维护的问题：

1. `OpenACC` 这种高层 directive-based 路线，是否真的能把 thermal LBM 跑得足够快？
2. 如果从单 GPU 扩展到多 GPU，最大的瓶颈到底在算力、内存、还是通信？
3. 在 `Fortran/OpenACC + MPI` 这样的代码基础上，应该优先优化哪几件事？

作者最后给出的答案非常明确：

- 单张 `NVIDIA A100` 上，2D 算例达到 `1.93 GLUPS`
- 单张 `NVIDIA A100` 上，3D 算例达到 `1.04 GLUPS`
- 这已经分别达到理论带宽上限的 `79.5%` 和 `76.7%`
- 强扩展到 `16 GPUs` 后，2D 达到 `30.42 GLUPS`
- 强扩展到 `16 GPUs` 后，3D 达到 `14.52 GLUPS`
- 弱扩展到 `16 GPUs` 时，并行效率仍高于 `99%`

所以这篇论文的真正结论不是“GPU 很快”，而是：

`thermal LBM 这种本身数据访问规则很强的算法，在 OpenACC + MPI 框架下，只要数据布局、域划分、通信调度做对了，完全可以做到很强的多 GPU 扩展。`

## 这篇文章真正解决了什么问题

如果只看标题，很容易以为它只是做了一个“thermal LBM on multi-GPU”的常规并行实现。但往下读会发现，它真正解决的问题比这个更具体：

### 1. 它不是在研究“公式能不能推导出来”，而是在研究“代码怎么不浪费硬件”

对热 LBM 而言，单步计算并不只是流场分布函数 `f_i` 的碰撞与传播，还要同时处理温度分布函数 `g_i`。这意味着相比纯流场 LBM：

- 内存读写更多
- halo 通信更多
- 子步骤更多
- 任务调度更复杂

所以 thermal LBM 的多 GPU 扩展难点，往往不在“数学上能不能写出 MRT”，而在“如何组织数据和任务，避免 GPU 和网络互相拖后腿”。

### 2. 它不是在证明 CUDA 才能高性能，而是在证明 OpenACC 也能做严肃的大规模计算

很多人会默认认为：真正想做极致性能，就必须手写 CUDA；像 OpenACC 这种高层指令方案，适合原型验证，不适合高端并行优化。作者基本上是在反驳这种刻板印象。

他们的思路是：

- 用 `OpenACC` 保持单卡代码简洁和可维护
- 用 `MPI` 负责跨 GPU 的同步
- 用 `CUDA-aware MPI + GPUDirect` 减少主机内存参与
- 再在任务调度上做精细优化

最后跑出来的结果说明，OpenACC 不是不能做高性能，关键在于你是否真正理解了程序的通信路径、内存行为和任务依赖。

### 3. 它把“多 GPU 为什么扩不动”说清楚了

这篇文章最有价值的一点，是作者没有只展示最终漂亮结果，而是先展示了一个“朴素版本”为什么不行。

最初他们采用的是一维域划分：

- 2D 沿 `y` 方向切
- 3D 沿 `z` 方向切

这样做的好处是数据在内存里比较连续，通信简单。但问题也很明显：随着 GPU 数量增加，每块 GPU 上的计算负载下降得很快，而边界通信量却不一定同步下降，于是通信占比越来越大。结果就是：

- 单卡性能不错
- 多卡总吞吐也会增长
- 但并行效率很快塌下来

特别是 3D 情况，`16 GPUs` 时朴素方案的并行效率已经掉到 `57%` 以下。作者不是一句“通信瓶颈”轻轻带过，而是把后面三种优化策略都明确建立在这个问题诊断之上。

## 引言值得借鉴的内容

### 1. 从高性能计算背景切入，而不是一开始就堆公式

这篇文章的引言写法很值得学。作者没有上来就丢 LBM 方程，而是先从后摩尔时代的高性能计算背景讲起：

- 晶体管继续缩小已经逼近物理极限
- 单核复杂化带来的性能增长越来越有限
- 未来性能增长更依赖并行架构而不是单核提速

这样一来，GPU 的出现就不是“工具选择”，而是“时代背景下的自然结果”。

### 2. 把 LBM 和 GPU 的适配关系讲得很自然

作者强调，LBM 之所以适合 GPU，不是因为它“新潮”，而是因为它天然具有：

- 局部数据依赖
- 规则的格点更新
- 大量重复的同构计算
- 很强的数据并行性

这类算法与 GPU 的 `SIMT` 执行模式天然匹配。换句话说，LBM 不是“勉强能上 GPU”，而是“天生适合 GPU”。

### 3. 引出 OpenACC 的逻辑很稳

作者没有把 OpenACC 说成“性能最好”的方案，而是把它放在“性能、可维护性、可移植性”三者之间的平衡点上：

- `CUDA/OpenCL`：细粒度控制强，但代码侵入性大
- `OpenACC/OpenMP`：侵入性更小，更便于从既有 Fortran/C 代码迁移

这段引言的潜台词非常值得借鉴：

`对大型科研代码来说，真正困难的不只是把程序第一次移植到 GPU，而是之后几年还能改、还能验、还能扩展到新平台。`

## 数学模型

### 1. 宏观控制方程

论文研究的是 `Boussinesq` 近似下的不可压缩热对流。它的物理假设是：

- 流体总体上按不可压缩处理
- 温度不是被动标量，而是通过浮力项反作用到速度场
- 粘性耗散和压缩功忽略
- 粘度、热扩散率等物性参数取常数

对应的宏观方程就是：

- 连续方程：`div u = 0`
- 动量方程：`du/dt + u·∇u = -(1/rho0)∇P + nu ∇^2 u + g beta_T (T-T0) e_g`
- 能量方程：`dT/dt + u·∇T = alpha_T ∇^2 T`

这里最值得注意的一点是：作者把温度明确看成 `active scalar`，也就是温度不是单纯随流场走，它会通过浮力项改变流动结构。

### 2. 无量纲化方式

作者采用的是以自由落体速度和自由落体时间为特征尺度的无量纲化。这一点和一些采用扩散时间尺度的热对流论文不完全一样。

他们的特征尺度大致是：

- 长度尺度：`H`
- 速度尺度：`sqrt(beta_T g H DeltaT)`
- 时间尺度：`sqrt(H / (beta_T g DeltaT))`

这样无量纲化后，方程里的系数变成：

- 动量方程扩散项前是 `sqrt(Pr / Ra)`
- 温度方程扩散项前是 `sqrt(1 / (Pr Ra))`

这组写法的物理意义是：作者选择的是“浮力主导”的尺度，而不是“扩散主导”的尺度。所以在阅读时不要把它和一些经典 2D RB 论文中写成 `Pr` 与 `Ra Pr` 的形式混为一谈。两者并不矛盾，只是无量纲化标尺不同。

### 3. 本文具体测试的物理构型

论文考虑的是：

- 2D 方腔
- 3D 立方腔

边界条件为：

- 左壁恒热
- 右壁恒冷
- 其余壁面绝热
- 所有壁面无滑移

控制参数为：

- `Pr = 0.71`
- 2D：`Ra = 10^8`
- 3D：`Ra = 10^7`

作者还特意说明，这两个工况在他们过去的研究中已经验证过，能够得到稳定流型；如果 `Ra` 再往上提，流场会转入非定常，并出现 `Hopf bifurcation`。这句话其实很重要，因为它说明本文不是在挑战更高物理复杂度，而是在一个已验证工况上，纯粹聚焦并行实现和性能优化。

## 热 LBM 模型细节

### 1. 双分布函数框架

作者使用标准 `DDF` 思路：

- `f_i`：负责流场
- `g_i`：负责温度场

其中：

- 2D：`D2Q9 + D2Q5`
- 3D：`D3Q19 + D3Q7`

这里为什么温度场不用和流场同阶的速度集合，而是用 `D2Q5/D3Q7` 这种更小的集合？作者给出的理由很直接：为了计算效率。也就是说，他们没有为了形式统一而给温度场配一个更重的速度集，而是选择了“够用且更省”的模型。

### 2. MRT 流场方程

流场分布函数满足 MRT 形式的演化方程：

`f_i(x + e_i dt, t + dt) - f_i(x,t) = collision + forcing`

碰撞项本质上是：

- 先把速度空间分布函数通过变换矩阵 `M` 投影到矩空间
- 在矩空间通过对角弛豫矩阵 `S` 进行不同模式的松弛
- 再变回速度空间

这里的关键不是公式本身，而是工程含义：

- `collision` 是局部操作，只依赖本格点数据
- `streaming` 会访问邻居格点，因此是通信敏感步骤

这为后面整个 OpenACC + MPI 的优化铺垫了结构基础。

### 3. 浮力项处理

作者采用的是带外力项的 MRT 流场 LBE。浮力项在 2D 和 3D 下分别沿重力方向进入宏观方程，并被映射到离散速度空间和矩空间中。

值得注意的是，这篇文章没有把重点放在重新设计 forcing scheme 上，而是沿用了成熟方案。也就是说，物理离散本身不是本文的创新点；它的创新点在于“如何让这套成熟方案在多 GPU 上不被通信和数据管理拖垮”。

### 4. 宏观量恢复

作者给出流场宏观量恢复方式：

- 密度：`rho = sum_i f_i`
- 速度：`u = (sum_i e_i f_i + 0.5 F) / rho`

这个 `+0.5F` 的修正项意味着外力处理是二阶精度一致的。虽然文章没有像一些理论论文那样展开大量 Chapman-Enskog 细节，但工程上这一步很重要，因为它确保计算出的宏观速度不是“漏了半步力项”的伪速度。

### 5. 温度场演化

温度分布函数 `g_i` 也采用 MRT 形式：

`g_i(x + e_i dt, t + dt) - g_i(x,t) = thermal collision`

宏观温度由：

- `T = sum_i g_i`

恢复出来。

温度边界条件处理为：

- 恒温边界：`half-way anti-bounce-back`
- 绝热边界：`half-way bounce-back`

这部分和你现在做的热 LBM 工作高度相关，因为它说明作者在并行优化时并没有改动温度边界处理逻辑，而是把边界条件作为既定正确模块保留下来，重点去优化数据交换和任务执行顺序。

## 为什么作者要把 collision 和 streaming 明确拆开

论文在实现层面特别强调，把 `f_i` 和 `g_i` 的更新都写成两个步骤：

1. `collision/relaxation`
2. `streaming/propagation`

这不是形式主义，而是后面所有并行优化的前提。

因为：

- `collision` 只依赖局部格点，是“纯本地计算”
- `streaming` 会把信息推到邻居，是“天然需要边界同步”

一旦你在代码里把这两步彻底拆开，就能比较自然地做三件事：

1. 单独统计碰撞和传播的耗时
2. 对内部节点先做局部计算
3. 把边界节点通信塞到合适的时间窗口里重叠掉

这也是本文最值得学的一点：作者并不是靠一条魔法 pragma 提速，而是先把算法结构整理成适合 GPU 和 MPI 编排的样子，再去谈优化。

## 测试设置与性能度量

### 1. 硬件平台

实验平台是一个四节点 GPU 集群，每个节点：

- `4 x NVIDIA A100`

节点间网络：

- `100 Gbps RoCE`

节点内 GPU 通信：

- 走 `PCI-e`

MPI 实现：

- `CUDA-aware OpenMPI`

并借助：

- `GPUDirect P2P`
- `GPUDirect RDMA`

这样 GPU 内存中的数据可以直接发往另一块 GPU 或网卡，不必绕经 host memory。这对多 GPU thermal LBM 非常关键。

### 2. 性能指标

作者采用两个指标：

- `MLUPS/GLUPS`
- 并行效率 `eta`

其中：

`MLUPS = 网格总点数 x 迭代步数 / 运行时间 / 10^6`

强扩展效率：

`eta = T1 / (n Tn)`

弱扩展效率：

`eta = T1 / Tn`

这种度量非常适合 LBM，因为它不纠结某个 kernel 的 GFLOPS，而是直接反映“单位时间推进了多少个格点更新”。

### 3. 为什么网格点数要用奇数

作者特别解释了为什么强扩展测试用的是：

- 2D：`8193 x 8193`
- 3D：`385 x 385 x 385`

而不是更顺手的偶数网格。

原因有两个：

1. 奇数网格可以减少某些伪守恒量引起的振荡
2. 对于 `half-way bounce-back / anti-bounce-back` 边界，奇数网格能让中心线或中心面恰好落在 `[(N+1)/2]` 位置，便于后处理和物理量提取

这一点很细，但也很实用。它说明作者不是只顾并行测试方便，而是兼顾了热对流后处理的准确性和一致性。

## 单 GPU 性能分析

### 1. 实测性能

朴素单卡性能已经相当高：

- 2D：`1931.2 MLUPS`
- 3D：`1042.4 MLUPS`

### 2. 为什么说这是 memory-bound

作者进一步估算理论带宽上限。每个格点一次迭代大致访问：

- 2D `D2Q9 + D2Q5`：`80` 个变量
- 3D `D3Q19 + D3Q7`：`143` 个变量

双精度下每个变量 `8 bytes`，而 A100 显存带宽是 `1555 GB/s`。于是理论上限约为：

- 2D：`2429.7 MLUPS`
- 3D：`1359.3 MLUPS`

实测值占理论上限：

- 2D：`79.5%`
- 3D：`76.7%`

这说明程序瓶颈非常明确地受显存带宽制约。换句话说，这已经不是“算术单元没吃满”的问题，而是“数据搬运能否足够高效”的问题。

这个判断对后面所有优化都非常重要，因为它告诉我们：

`thermal LBM 的多 GPU 优化，本质上是内存与通信优化，而不是单纯的浮点优化。`

## 朴素多 GPU 实现

### 1. 为什么最初选择一维切分

在 Fortran 列主序下，数据沿 `x` 方向连续。于是作者最初采用：

- 2D 沿 `y` 方向分块
- 3D 沿 `z` 方向分块

这样子域接口是：

- 2D：沿 `x` 的线
- 3D：沿 `x-y` 的面

好处是边界消息天然更连续，便于直接发送。

### 2. ghost layer 的作用

每个子域外面加 ghost 层，用来接收邻居子域边界信息。这个 ghost layer 不是可有可无的细节，而是多 GPU streaming 的核心缓存区。

### 3. 作者没有发送完整数组，而是只发必要速度分量

这是论文里非常有工程味道的一点。作者指出，在 streaming 阶段，不必把完整的 `f_i^+` 或 `g_i^+` 整个边界都发走，而是只发真正会穿越边界的那些离散速度分量。

例如 2D 情况下，如果上边界和下边界分别与相邻子域相接，那么：

- 发往上邻居的是会向上传播的那些 `f_i` 分量和对应 `g_i`
- 发往下邻居的是会向下传播的那些 `f_i` 分量和对应 `g_i`

这一步直接减少了消息体积。

### 4. 为什么朴素方案扩不动

作者把原因说得很清楚：

1. 强扩展时，每块 GPU 计算量减少很快
2. 但每块 GPU 的边界通信量并不会按同样速度减少
3. 所以通信时间占总时间的比例上升
4. 当子域太小，GPU 甚至不能被充分占满，kernel launch overhead 也会显著

这两种效应叠加，导致 3D 朴素一维切分在 `16 GPUs` 时并行效率已经很差。

## 第一类优化：块划分

### 1. 基本思想

作者引入 `block partitioning`，也就是在多个方向上同时切分区域，而不是只沿一个方向切。

他们给出的划分方案是：

- `2 GPUs`：2D 为 `1x2`，3D 为 `1x1x2`
- `4 GPUs`：2D 为 `2x2`，3D 为 `1x2x2`
- `8 GPUs`：2D 为 `2x4`，3D 为 `2x2x2`
- `16 GPUs`：2D 为 `4x4`，3D 为 `2x2x4`

### 2. 这一步为什么对 3D 更有效

直觉上，多维切分会增加邻居数量，所以听起来不一定更好。但作者做了一个非常有价值的简单模型分析。

对于边长为 `N` 的 2D 方域，若使用 `a` 个 GPU：

- 一维切分时，每块 GPU 发送 `2N` 个边界点
- 二维块切分时，每块 GPU 发送 `4(N/sqrt(a) + 2)` 个边界点

再把每发送一个边界点的时间记为 `k`，每启动一次通信 kernel 的额外开销记为 `h`，则：

- 一维切分：`t1 = 2kN + 2h`
- 块切分：`t2 = 4(N/sqrt(a) + 2)k + 4h`

于是只有当：

`t1 > t2`

也就是当 `N` 和 `a` 都足够大时，块划分才会真正划算。

这段分析特别值得记下来，因为它不是简单说“块划分更先进”，而是明确告诉你：

`块划分不是永远更好，它是在大规模 3D 问题和较多 GPU 数量下才开始体现优势。`

这也解释了文中的现象：

- 对 3D，块划分明显改善性能
- 对 2D，块划分甚至可能略微变差

### 3. 不要迷信 MPI derived datatype

作者还专门提醒，在 `CUDA-aware OpenMPI` 下，即使支持非连续 datatype，也不一定值得直接用。原因是底层可能仍要把碎片数据拷到中间 buffer，开销不小。

他们更推荐：

- 手动 pack 边界数据
- 放进连续 buffer
- 再做发送

这对 Fortran 尤其重要，因为列主序下某些方向的边界本来就是非连续的。

## 第二类优化：通信与计算重叠

### 1. 为什么这一步是核心

块划分只是减少了通信量，但没有改变一个根本事实：跨 GPU 的 halo 同步迟早还是要发生。于是下一步自然就是：

`能不能在通信发生时，让 GPU 干别的活？`

作者的答案是可以。

### 2. OpenACC 的异步队列怎么用

在 OpenACC 里，他们使用：

- `!$acc async`
- `!$acc wait`

来创建异步工作队列。基本逻辑是：

1. 先更新边界节点，并把需要发送的数据打包到连续 buffer
2. 启动异步消息传输
3. 同时在 GPU 上继续计算内部节点
4. 在真正需要边界数据之前，再做 `wait`

这样通信延迟就被“藏”在内部节点计算时间后面了。

### 3. thermal LBM 为什么特别适合做重叠

作者指出，在单个时间步里：

- 流场分布函数 `f_i`
- 温度分布函数 `g_i`

是两套相对独立的演化链条。于是你不仅能做“边界通信 vs 内部计算”的重叠，还能做“`f_i` 的一部分工作 vs `g_i` 的一部分工作”的交叉调度。

### 4. 论文给出的 3D 调度顺序非常值得抄

这是全篇最实用的一段之一。作者把 `f_i` 的通信进一步拆成三组：

- `f_x`：前后表面
- `f_y`：左右表面
- `f_z`：上下表面

然后安排成大致这样的顺序：

1. 先在内部节点上做 `g_i` 的 relaxation，同时通信 `f_z`
2. 再在边界节点上处理 `g_i` 通信，同时在内部做 `f_i` 的 relaxation
3. 继续用 `f_i` 内部 relaxation 去掩护 `f_y` 通信
4. `f_x` 的通信则让 `g_i` 的 propagation 和温度宏观量计算去掩护

这说明作者不是粗粒度地说“overlap communication with computation”，而是真正分析了：

- 哪一段 kernel 最耗时
- 哪一类消息最适合被谁掩护
- 哪些依赖关系必须等
- 哪些可以交叉

### 5. 这一步带来的收益

通信重叠的收益非常明显，尤其是 3D：

- 8 GPU 时，3D 并行效率从 `78.7%` 提升到 `97.1%`
- 16 GPU 时，吞吐提升约 `1.28x`

这组结果非常说明问题：真正让多 GPU 程序塌掉的，往往不是“总通信量太大”，而是“通信发生的时机太蠢”。

## 第三类优化：单 GPU 并发计算

### 1. 数据并行之外，还可以挖任务并行

前两步优化主要解决的是：

- 数据怎么放
- 子域怎么切
- 通信怎么藏

第三步作者进一步利用 GPU 的多队列能力，把 `f_i` 和 `g_i` 的独立任务放到不同异步队列里并发执行。

### 2. 这一步的收益为什么没有前一步大

单卡并发的收益是有的，但没有通信重叠那样剧烈。原因也很好理解：

- 通信重叠是在隐藏真正昂贵的跨设备等待
- 单卡并发更多是在提高片上资源利用率

所以它的作用更像“最后一层精修”，而不是“决定性翻盘”。

### 3. 论文里的一个有趣现象

作者提到，2D 情况下并行效率甚至可能略高于 `100%`。他们的解释是：

- 多 GPU 后，每张卡上的工作块更适合片上缓存与调度
- 任务并行带来了更好的资源利用

这说明并行效率偶尔超线性，并不一定意味着测错了，也可能是硬件利用方式确实更好了。

## 强扩展与弱扩展结果

### 1. 强扩展

固定总问题规模：

- 2D：`8193 x 8193`
- 3D：`385 x 385 x 385`

最终优化后的结果：

- 2D：`30.42 GLUPS` on `16 GPUs`
- 3D：`14.52 GLUPS` on `16 GPUs`

### 2. 弱扩展

固定每张卡的子域大小：

- 2D：`8192 x 8192 / GPU`
- 3D：`384 x 384 x 384 / GPU`

对应结果：

- 1 GPU 时约 `1932.9 MLUPS` 和 `1045.3 MLUPS`
- 扩展到 `16 GPUs` 时，吞吐几乎线性增长
- 并行效率始终高于 `99%`

弱扩展成绩这么漂亮，说明作者的实现不只是“某个固定规模刚好调得不错”，而是整体架构真的比较健康。

## CPU 与 GPU 对比

附录中作者还给了 CPU 版基线。CPU 代码使用的是：

- `MPI + OpenMP`

每个 CPU 节点配的是：

- `2 x Intel Xeon 6258R`

并且他们讨论了一个很现实的问题：每个节点到底应该用多少 MPI 进程、每个进程配多少 OpenMP 线程。作者最后选择的是：

- `4 MPI processes x 14 OpenMP threads`

他们给出的理由也很典型：

- OpenMP 线程太多，跨 socket 访问和 OpenMP 开销会上升
- MPI 进程太多，通信开销和内存占用会上升

这个附录虽然不是主线，但很有价值，因为它提醒我们：

`GPU 代码快，不是因为 CPU 代码写得差，而是因为 thermal LBM 这类 memory-bound 且高规则性的算法，确实更适合 GPU。`

## 这篇论文对我当前代码最直接的启发

### 1. 如果我现在在写 `3DRBOpenaccMpi.F90`，首先该看什么

不是先去改某个 MRT 参数，而是先检查下面几件事：

1. `f_i` 和 `g_i` 是否已经在代码结构上彻底拆成 collision / streaming 两段
2. halo 通信是不是只发送真正跨边界的速度分量
3. 非连续边界是不是手动 pack 成连续 buffer
4. 是否已经用了 `async/wait` 去重叠边界通信与内部节点计算
5. `f_i` 和 `g_i` 是否可以进一步分配到不同异步队列

### 2. Fortran 数据布局真的要顺着列主序来想

这篇文章一个很重要的工程提醒是：你不能抽象地想“域划分”，而必须结合 Fortran 的实际内存连续方向去想。

对于 `f(x,y,z,i)` 这类列主序数组：

- `x` 通常是最连续的
- 沿 `x` 的切片常常最好搬
- 沿其他方向的边界则往往要显式 pack

这件事如果一开始不设计好，后面越并行越痛苦。

### 3. 如果现在只做了一维切分，下一步最值得试什么

如果你当前实现还是单一方向划分，那么非常自然的下一步就是：

- 在 3D 情况下尝试块划分
- 同时保留手动 pack 的边界缓冲区

但这一步并不是无条件马上上。根据本文的分析：

- 对 2D 小问题，块划分未必更好
- 对 3D、大规模、更多 GPU 数量，块划分价值更大

所以它不是“代码风格升级”，而是“扩展规模达到一定程度后的必要优化”。

### 4. thermal LBM 的重叠机会比等温 LBM 更多

因为你有两套分布函数：

- `f_i`
- `g_i`

它们天然提供了更多任务交错空间。也就是说，thermal LBM 虽然通信更重，但也比单分布函数 LBM 更有机会通过调度把等待藏掉。这一点非常值得在你当前代码里主动利用。

### 5. 所有性能测试都用双精度，这一点非常关键

作者所有结果都是 `double precision`。这不是小事。因为很多 GPU 加速论文会在性能上占便宜，但 quietly 切到单精度。本文没有这么做，这意味着它给出的性能数字对真正做高 Rayleigh 数热对流的人更有参考价值。

## 这篇论文的局限

虽然这篇论文很有价值，但也要看到它的边界。

### 1. 它主要讲的是并行实现，不是新的数值稳定性理论

所以你不能拿它来替代更专门的 MRT 热 LBM 理论论文。

### 2. 它验证的是侧壁加热对流

这和你关心的 `RB` 问题有重合，但不完全一样。它能告诉你多 GPU 框架怎么搭，不等于它已经替你验证了更复杂工况下的稳定性与精度。

### 3. 它的性能数字带有硬件平台属性

`A100 + RoCE + CUDA-aware OpenMPI + GPUDirect`

这是一套很强的硬件/软件组合。所以具体 GLUPS 数字不能机械照搬到别的平台上，但优化思路是可以迁移的。

## 一句话总结

这篇论文最值得记住的一句话可以是：

`它不是在教你再发明一个 thermal LBM，而是在教你怎样把已经成熟的 thermal LBM 真正组织成一套可扩展的多 GPU 工程代码。`

对我当前代码最有价值的，不是它又写了一遍 `D3Q19` 和 `D3Q7`，而是它把下面这条工程路线讲清楚了：

`SoA 布局 -> 只传必要 halo -> 手动 pack 连续 buffer -> 多维块划分 -> async/wait 重叠通信 -> f/g 双分布并发`

如果后面我要继续把 `3DRBOpenaccMpi.F90` 往真正可扩展的多 GPU 版本推进，这篇论文基本可以当成实现路线图来用。
