Abstract
The lattice Boltzmann method (LBM) is a mesoscopic numerical technique widely
used for solving partial differential equations such as the Navier–Stokes equations
or advection–diffusion equations. It employs discrete particle distribution functions
instead of macroscopic variables, offering advantages in parallelization and scal-
ability. This paper introduces the TNL-LBM project, an advanced computational
framework that implements LBM using the Template Numerical Library (TNL).
TNL-LBM is designed for high-performance, large-scale simulations of turbulent
flows and is available under the MIT license. The project emphasizes modularity,
efficiency, and flexibility, providing a library of fundamental components and a
high-level framework for developing custom solvers. Key features include a mod-
ular architecture with pluggable components, high performance through parallel
algorithms and data structures provided by TNL, and scalability across multi-core
CPUs, GPU accelerators, and distributed platforms. The paper outlines the compo-
nents of LBM, its computational algorithm, and the design of TNL-LBM, followed
by a description of input/output components and benchmark results demonstrating
its performance on the Karolina supercomputer and on a compute node based on
NVIDIA Tesla H100 accelerators. The performance of TNL-LBM is also compared
to other open-source LBM projects.

1 Introduction

The lattice Boltzmann method (LBM) is a mesoscopic numerical method capable
of solving a suitable class of partial differential equations such as the advection–dif-
fusion or Navier–Stokes equations [13, 16, 23]. It uses a discrete set of particle dis-
tribution functions as main unknown variables instead of the original macroscopic
variables. It has been extensively studied for the past couple of decades and has
developed as an alternative numerical method to the classical finite element, finite
volume, and finite difference methods. LBM was originally used for the numerical
solution of the incompressible Navier–Stokes equations [35] and has been extended
to various types of problems, such as fluid-solid interaction [10, 14], multiphase,
multi-component and porous media flows [23], chemical and thermal transport [8,
50], radiative transport [41, 42], non-Newtonian fluid flow [11], and other problems.
The method can be easily and efficiently parallelized [35], and the advent of general-
purpose computing on graphics processing units (GPGPU) made large-scale and
highly resolved numerical simulations of turbulent flows feasible [18, 27, 36, 47, 59,
60].
   This paper describes the TNL-LBM project, an advanced computational frame-
work implementing the lattice Boltzmann method using the Template Numerical
Library (TNL) [46]. Both TNL-LBM1 and TNL2 are free and open-source projects
available under the MIT license. TNL-LBM is a high-performance code designed to
facilitate large-scale simulations using LBM, including problems involving turbulent
flow and coupling with additional solvers. It has been used in numerous scientific
and engineering applications, including environmental science, biomedical engi-
neering, or the energy industry, where it has shown its versatility, robustness, and
effectiveness. The implementation of LBM in this project was verified and validated
on multiple problems in [5, 9–11, 13–16, 29]. We would like to highlight that these
works include various multiphysics problems that require extensions of the lattice
Boltzmann method developed within the TNL-LBM project, such as non-Newtonian
fluid flow, fluid–structure interaction based on the immersed boundary method, and
coupling with the mixed-hybrid finite element method (MHFEM).
   The TNL-LBM project emphasizes modularity, efficiency, and flexibility. From
the user’s perspective, the repository contains functionality that can be used in dif-
ferent ways. First, there is a library of fundamental low-level components that are
needed for LBM, such as collision operators, streaming schemes, data structures,
and parallelization algorithms. On top of this, the TNL-LBM project provides a gen-
eral high-level framework for writing LBM-based solvers and a few simple exam-
ples that show how to adapt the code for a particular problem. Using the framework
is not as versatile as using the library, since it enforces certain design patterns, but it
simplifies the development of custom solvers, since researchers do not need to deal
with designing a solver from scratch and they can instead focus on obtaining desired
results. The key features of the project include the following.

1.1 Related work

Several LBM implementations exist as active free and open-source projects, includ-
ing Palabos [38], OpenLB [34], waLBerla [3], TCLB [37], and VirtualFluids [20].
These projects share common features such as GPU acceleration, distributed com-
puting via MPI, and various multi-physics capabilities. Beyond standard incom-
pressible flow, Palabos, OpenLB, and waLBerla can be applied to problems involv-
ing porous media, particles, free surface, thermal, or multi-phase flows. Similarly,
TCLB is extended to problems with particles, thermal or multi-phase flows and Vir-
tualFluids is an active research code with many emerging multi-physics extensions.
However, the main differences of these projects lie in their design choices, program-
ming interfaces, and implementation of LBM-specific components.
   TNL-LBM distinguishes itself through its full support for distributed GPU-accel-
erated systems, modular architecture with pluggable components, and a permissive
MIT license. The core TNL library serves as a performance portability layer for
TNL-LBM, providing support for various hardware platforms without code changes
in downstream projects. It also extends to multi-physics problems via models for
solving thermal or non-Newtonian flows and coupling with the mixed-hybrid finite
element method (MHFEM) and immersed boundary method (IBM).
   Table 1 summarizes the key features of the aforementioned projects. In addition,

coupling with external software projects, etc. This paper describes details related to
the components implemented in the TNL-LBM project, but a comprehensive review

2 LBM components and background

The lattice Boltzmann method [35] (LBM) is an alternative to traditional compu-
tational methods for the solution of time-dependent PDEs such as finite difference,
finite volume, and finite element methods. Based on the kinetic theory of gases,
it utilizes probabilistic distributions as main degrees of freedom, with the origi-
nal macroscopic variables reconstructed as raw moments. The approach based on
kinetic theory makes LBM very suitable for parallel computations. However, it also
poses several challenging problems such as the treatment of boundary conditions
(see Sect. 2.5).
   The detailed derivation of LBM is not within the scope of this article. Instead, we
review the basic components related to the implementation of LBM within the pre-
sented TNL library. For further details on LBM, the reader is referred to [16, 23, 35].

2.4 Equilibrium function

In the kinetic theory of gases, the Maxwell–Boltzmann distribution f eq describes
the speeds of particles in an ideal gas that moves with a macroscopic velocity v in a
thermodynamic equilibrium [35]. In the derivation of the discrete lattice Boltzmann
equation, the equilibrium distribution function f eq is discretized to obtain an approx-
imation of the equilibrium state for the given discrete velocity set.
   The form of the discrete equilibrium function is based on the solved problem
and the chosen collision operator. For instance, a second-order approximation of
the continuous Maxwell–Boltzmann distribution [35] and the entropic equilibrium
model [31] are implemented in TNL-LBM.

2.5 Boundary conditions

The formulation of proper boundary conditions for LBM is a major complication
in its applications, since the desired macroscopic conditions (e.g., given in terms of
𝜌 and v) must be reproduced at the mesoscopic level using the discrete density dis-
tribution functions fq [35]. This problem does not have a unique solution, and thus
multiple LBM boundary schemes exist that approximate the same macroscopic con-
dition. The following boundary conditions are currently implemented in TNL-LBM:

•   General Dirichlet boundary condition based on the equilibrium approach [35]
•   Inflow boundary condition based on the equilibrium approach [35]
•   Interpolated outflow boundary condition [12]
•   No-slip boundary condition based on the bounce-back approach [35]
•   Moment-based boundary conditions [12]
•   Periodic and symmetry-plane boundary conditions [35]

Note that all boundary conditions that are currently implemented in TNL-LBM use
values only from the closest layer of neighboring lattice sites. This property sim-
plifies the implementation and interaction of boundary conditions with other com-
ponents of the TNL-LBM project, such as streaming patterns and communication
in distributed computing. Considering a more general class of non-local boundary
conditions might limit the number of available streaming patterns.

2.7 Streaming schemes

Based on Equation (2), the computational steps needed to evolve the state from
the current time t to the next time level t + Δt can be decomposed into two suc-
cessive steps: the collision step and the streaming step. Depending on the order of
these steps, two simple yet equivalent schemes can be formulated [35]. In the push
scheme, the collision step is performed first and the subsequent streaming step prop-
agates the post-collision values fq∗, of the distribution function from the reference
lattice site x ∈ LΩ to the neighboring lattice site in the direction of the correspond-
ing velocity 𝝃 q ∈ V , for all q ∈ {1, … , Q}:
                                                   (                     )
                        fq∗ (x, t) = fq (x, t) + Δt Cq (x, t) + Sq (x, t) ,        (6a)

                              fq (x + Δt𝝃 q , t + Δt) = fq∗ (x, t).                       (6b)

    On the other hand, in the pull scheme, the streaming step first propagates the
post-collision distribution function fq∗ to the reference lattice site x ∈ LΩ from the
neighboring lattice site in the direction of −𝝃 q from the previous time level, and the
subsequent collision step computes the new post-collision distribution functions fq∗
at the current time level t, for all q ∈ {1, … , Q}:
                              fq (x, t) = fq∗ (x − Δt𝝃 q , t − Δt),                        (7a)

                                                  (                     )
                       fq∗ (x, t) = fq (x, t) + Δt Cq (x, t) + Sq (x, t) .                (7b)

   Note that regardless of the chosen streaming scheme, the collision step is local in
terms of the lattice sites x ∈ LΩ (that is, collisions in different lattice sites are inde-
pendent of each other), but collective for all q ∈ {1, … , Q} since the collision opera-
tor Cq depends on the entire set of discrete density distribution functions at the given
lattice site. On the other hand, the operations in the streaming step are non-local, but
trivial as they do not require any computation (the post-collision values are merely
transferred from one place to another).
   Both the push and pull schemes require attention during the implementation to
avoid overwriting memory locations containing values that may be needed in the
future. In the former scheme, the values of fq at the time level t + Δt cannot be
pushed to the neighboring lattice sites by overwriting the values at the current time
level t, because the neighboring nodes may still be unprocessed in this time step.
Similarly, after the collision step in the pull scheme, the values of fq∗ cannot over-
write the values of fq at the reference lattice site, because those values may be pulled
later when processing neighboring nodes in the same time step. Hence, the imple-
mentation of these schemes requires the use of two arrays to store the state of the
simulated system. In each time step, an array A is used for input and an array B is
used for output, and while going to the next time step (that is, from t to t + Δt ), the
arrays A and B are swapped. Hence, this approach is named A-B pattern. The A-B
pattern with the pull scheme is implemented in the TNL-LBM project.
TNL‑LBM: Scalable lattice Boltzmann method implementation…            Page 9 of 35   167


    The A-A pattern [2, 58] is an alternative approach that allows to perform the
streaming step in-place using just one storage array 𝙰 for the density distribution
functions. This feature of the streaming scheme reduces the memory requirements
for a given lattice by a factor of two, which is crucial for high-resolution LBM simu-
lations on GPU accelerators due to their limited amount of global memory. The A-A
pattern is also implemented within the TNL-LBM project.
    The time-stepping procedure using the A-A pattern involves different opera-
tions in even and odd iterations. In an even iteration, both pre-collision reading and
post-collision writing operations happen locally at the reference lattice site x ∈ LΩ,
whereas in an odd iteration, both pre-collision reading and post-collision writing
operations access only neighboring lattice sites. In order to avoid read/write con-
flicts in the storage array, the A-A pattern involves inverting the streaming direction
𝝃 q at the end of even iterations and at the beginning of odd iterations.
    The A-A pattern is not the only technique that facilitates in-place streaming using
a single array. Alternatives include, for example, Esoteric twist [17], the compact
LRnLA streaming pattern [60], Esoteric push, and Esoteric pull [39]. However, none
of the aforementioned papers discuss advanced topics such as MPI communication
or the implementation of boundary conditions. Hence, these streaming patterns have
not yet been implemented in the TNL-LBM project.

    In order to utilize multiple GPUs or even multiple nodes for computing in a dis-
tributed fashion, an additional level of coarse-grained parallelism has to be intro-
duced based on the domain decomposition approach. The global lattice LΩ is
divided into subdomains LΩ,j , j ∈ {1, … , Nparts } that are processed independently
using Nranks ≤ Nparts independent processes (MPI ranks). Each subdomain is
assigned one MPI rank that is mapped to one coarse-grain computational unit, such
as a CPU core, a CPU socket, or a GPU accelerator. Each MPI rank is responsible
for processing computations related to one or more subdomains that were assigned
to it. In order to obtain consistent results, it must be ensured that the values of dis-
crete density distribution functions are propagated correctly across the interfaces
between subdomains. However, due to the distributed memory system, this cannot
happen automatically as part of the streaming step in Algorithm 1. The solution
adopted in our implementation is to extend each subdomain LΩ,j with ghost lattice
sites which are excluded from parallel processing but provide additional storage
where other lattice sites will write and/or read values that will be later streamed to/
from the adjacent subdomains. After the parallel loop in each time step, the data
corresponding to the ghost lattice sites are exchanged via MPI among adjacent sub-
domains. The implementation of this procedure is explained later in Sect. 4.2.

4 Extensible design and composition of components in a simulation

From a high-level point of view, each MPI rank creates an object of the State
class, which combines all the components needed to run a simulation.
   The implementation of State provides all functionality needed for solving
problems such as the Navier–Stokes equations. However, it is not tied to a par-
ticular problem and all problem-specific logic is implemented in separate compo-
nents. The State class is designed to be extended via inheritance, so users can
define their own subclass for a particular case and adjust the behavior of the solver
by adding attributes and overriding various virtual member functions. Hence, it is
possible to implement more complicated solvers for coupled problems, such as the
Navier–Stokes–Fourier problem of fluid flow coupled with thermal transport [8, 50].
   The class diagram of State is shown in the left half of Fig. 1. The State
class has an attribute of the LBM class that represents one set of discrete distribu-
tion functions. Additional sets of discrete distribution functions can be represented
by additional attributes in a user-defined class inheriting from State. Next, each
LBM instance has a vector of LBM_BLOCK objects that represent the decomposition
of the lattice into subdomains and additional functionality related to LBM simula-
tions, such as variables for time-stepping or conversion between physical and lattice
units. By default, each MPI rank manages just one LBM_BLOCK, but in general it
can utilize multiple blocks that may be necessary to add for optimal load-balancing
in case of non-uniform decomposition. Finally, the LBM_BLOCK class contains all
data related to the given subdomain, which is stored in data structures that will be
described later.
   The implementation approach based on the extension of the State class is suita-
ble for high-level adaptations that reuse various internal data structures. However, it
is often necessary to modify even the low-level building blocks of the lattice Boltz-
mann method, such as local per-lattice-site computations in the LBM algorithm. For
example, it may be desirable to switch to a different collision operator or to define
additional macroscopic quantities. In order to sustain high-performance computing
on GPU accelerators that have limited support for virtual functions [43], using com-
pile-time techniques rather than dynamic polymorphism is more appropriate. There-
fore, our LBM implementation is based on several template meta-programming

4.1 Internal data structures

The TNL-LBM project relies on the Template Numerical Library (TNL) [46] for
the parallel programming model and internal data structures used for the LBM algo-
rithm. TNL is a collection of building blocks that facilitate the development of effi-
cient numerical solvers and HPC algorithms, providing native support for modern
hardware architectures such as multicore CPUs, GPUs, and distributed systems,
which can be managed via a unified interface. TNL is a state-of-the-art parallel com-
puting library comparable to, for example, Kokkos [53, 54].

The SizesHolder, Permutation, and Overlaps parameters allow to
specify any memory layout, including the distinction between static and dynamic
sizes separately for each dimension of the array. Moreover, thanks to Permuta-
tion, the logical ordering such as Q × Nx × Ny × Nz for the array of distribution
functions, is independent from the data layout ordering. For example, the afore-
mentioned 4-dimensional array in TNL-LBM is configured with a permutation
(0, 1, 3, 2), such that the index along the y-dimension changes the fastest, followed
by the z-dimension and x-dimension, and the index of the distribution function
q ∈ {0, 1, … , Q − 1} changes the slowest. This data layout is advantageous for the
performance of MPI communication in the case of a simple 1D domain decomposi-
tion along the x-axis (see also Sect. 4.2).
   The global array corresponding to the lattice LΩ must be decomposed in a struc-
tured conforming manner (i.e., subdomains must be orthogonal blocks arranged in
a conforming grid) and the decomposition must be consistent for all the aforemen-
tioned arrays, but each rank can be assigned multiple subdomains and the rank num-
bering is arbitrary. All distributed data structures are collected in the LBM_BLOCK
class that contains all data associated with one subdomain: local subarrays, subdo-
main sizes and offsets, indices of neighboring blocks, and ranks that own them.
   To facilitate computations on GPU accelerators, two objects are needed for each
array to represent data in different memory spaces. One object allocates the array
data in the host memory where it can be processed by the CPU, and the other object
allocates the array data in the device memory where it can be processed by the GPU
accelerator. The main part of the LBM (that is, steps 8 and 9 in Algorithm 2) is
computed on GPU accelerators, but CPU processing is used for initialization and
output of the results. During the computation of the LBM algorithm, relevant arrays
must be copied from one memory space to another whenever processing is switched
from CPU to GPU or vice versa. Furthermore, the LBM_BLOCK class contains an
instance of LBM_DATA​(see Fig. 1), which provides access to all data that is needed
from a running GPU kernel. This includes pointers to the arrays allocated in the
device memory, sizes of the lattice, and scalar parameters (e.g., viscosity and param-
eters related to boundary conditions).

4.2 Optimization remarks

The most important optimization for distributed LBM computations is already
described in Algorithm 2: Processing interior lattice sites must overlap with data
synchronization on the interfaces between adjacent subdomains. This technique
is implemented by launching multiple GPU kernels in different streams and using
stream-level synchronization functions [43]. A separate stream is used for each
interface with an adjacent subdomain and for the interior lattice sites. The streams
for interfaces are configured with the highest priority so that the operations in these
streams are executed as soon as possible. The stream for the interior is configured
167     Page 16 of 35                                                     J. Klinkovský et al.


with the lowest priority, as it is used for the longest-running kernel that is waited for
at the end of the time step.
    Data synchronization among the ranks of adjacent subdomains is governed by
the DistributedNDArraySynchronizer class from the Template Numeri-
cal Library (TNL) [52]. A synchronizer object is created for each subdomain and
each of the Q discrete distribution functions. It is responsible for synchronizing data
in one subarray to and from neighbors in the direction of the corresponding vector
from the velocity set. For example, when the D3Q27 velocity set is used and the lat-
tice is distributed in a 1D manner such that each subdomain has at most two neigh-
bors, one to the left and one to the right, 9 distribution functions (corresponding to
discrete velocities with +1 in the first component) are synchronized from left to right
on each interface, and different 9 distribution functions (corresponding to discrete
velocities with −1 in the first component) are synchronized from right to left. Note
that in case of a 2D or 3D decomposition, the communication pattern is more com-
plicated as it is necessary to also synchronize relevant distribution functions across
edges and corners of the interfaces between subdomains.
    The synchronizer objects are used in Algorithm 2 in the steps 4 and 12. The
synchronization procedure utilizes pipelining among all synchronizers to hide the
latency of internal operations. Note that the implementation relies on the so-called
CUDA-aware support [32] from the MPI library to avoid having to explicitly copy
the send and receive buffers from the GPU memory to the host memory. However,
unless NVIDIA GPUDirect technology [44] is functional, the MPI library may still
need to internally copy data between the GPU and host memory when processing
requests such as MPI_Isend or MPI_Irecv.


5 Data management and visualization

Efficient data management is essential for large-scale scientific simulations, as inad-
equate input/output (I/O) components can render the simulation impractical or even
unusable. The TNL-LBM project addresses this challenge by using the ADIOS2
(Adaptable Input/Output System) library [22]. ADIOS2 is a cutting-edge library for
scientific data management, offering a flexible framework for high-performance data
I/O that is capable of processing terabytes of data per rank in exascale distributed
workloads.
   ADIOS2 serves two primary purposes in the TNL-LBM project: saving output
data for visualization of the simulation results and checkpointing the simulation
state to facilitate restarts from the last saved state.

5.1 Visualization output

The ADIOS2 library provides a generic interface that can be used to construct vari-
ous data hierarchies without enforcing a specific data layout. Two notable exam-
ples of data models that utilize ADIOS2 are Fides [48] and the vtk.xml attribute
[21]. These models enrich the dataset with metadata that maps binary data arrays to
TNL‑LBM: Scalable lattice Boltzmann method implementation…          Page 17 of 35   167


visualization objects, enabling seamless integration with visualization tools such as
ParaView [1]. An example of such visualization is shown in Fig. 2.
   Compared to our previous approach of directly writing VTK files from the simu-
lation codes, the current method retains full management of large data arrays within
ADIOS2, ensuring high efficiency and scalability of the visualization pipeline.
Moreover, ADIOS2 is not limited to the post-processing workflow, which involves
saving output data to files on disk and processing them with external tools. By
changing the engine type in the ADIOS2 configuration, the workflow can be adapted
for in situ or in-transit visualization [40] while using the same metadata mapping
attached to the ADIOS2 dataset. Exploring these advanced workflows in the TNL-
LBM project is an ongoing effort.

5.2 Checkpointing

The flexibility of the ADIOS2 library in data layout makes it an ideal choice for
checkpointing in the TNL-LBM project. Checkpointing involves saving the com-
plete state of a running simulation and restoring it after a restart. This functional-
ity allows to save the full simulation state before the allocated computation time
expires and to resume the simulation from the last saved state in a new instance.
Checkpointing enables splitting long simulations into several chunks that fit within
the HPC system’s maximum wallclock time limit, facilitating both time-constrained
execution and crash recovery.
   This approach results in a custom data hierarchy comprising large data arrays for
all density distribution functions, boundary conditions, and scalar parameters of the
simulation. Given the large memory requirements of the lattice Boltzmann method,
the amount of data for checkpointing often exceeds the size of a single visualization
snapshot, making the efficiency of the underlying I/O system critical.
   Creating a checkpoint can be time-consuming and may run out of the allocated
time limit, potentially leading to an incomplete state in the file. To prevent the cor-
ruption of the previous checkpoint, we implement a protection mechanism. The
new state is written to a temporary file/directory and atomically exchanged with the
previous state on disk upon successful completion. In Linux, this is achieved using
the renameat2 system call with the RENAME_EXCHANGE parameter [7]. This
approach ensures that if the new checkpoint fails to complete, the previous check-
point remains intact, allowing the simulation to be safely restarted from the last
valid state.

6.2.2 Strong‑scaling study

In the strong-scaling analysis, the global lattice size remains fixed (512 × 512 × 512),
while the subdomains become smaller as the number of MPI ranks increases. The
corresponding problem size (16 GB in single precision, 32 GB in double precision)
approaches the 40 GB memory limit of a single NVIDIA A100 GPU, restricting
further scaling. The physical dimensions of the domain are Lx = Ly = Lz = 0.25 m.
    The results from NVIDIA A100 GPUs on the Karolina supercomputer, sum-
marized in Table 4 and Fig. 7, demonstrate near-ideal scalability up to 16 ranks (2
nodes), with efficiency dropping as the number of ranks ( Nranks) increases. For sin-
gle precision, efficiency decreases from 0.99 at 8 ranks to 0.87 at 32 ranks and fur-
ther to 0.45 at 128 ranks. Double precision maintains higher efficiency across all
scales, reaching 0.64 at 128 ranks. This disparity arises because double precision
computation, though slower per rank, allows better overlap with communication due
to longer kernel execution times. Single-precision runs, constrained by shorter com-
putation times, exhibit less effective hiding of communication latency, particularly
at large Nranks.
    Communication bottlenecks emerge as subdomains shrink. Due to the 1D decom-
position used in this study, the subdomains are reduced to 4 × 512 × 512 elements
at 128 ranks, with the communication volume per rank remaining constant (faces of
subdomains). This leads to a growing communication-to-computation ratio, limit-
ing scalability as communication eventually starts to dominate the total runtime. A
multidimensional decomposition could mitigate this by distributing the communica-
tion volume more evenly, at the cost of increased latency (in 1D decomposition we
TNL‑LBM: Scalable lattice Boltzmann method implementation…                       Page 25 of 35     167


can configure the storage layout such that all communicated values are stored con-
tiguously in memory, but in multidimensional decomposition this is not possible).
However, such approach was not tested due to limited access of the authors to the
Karolina supercomputer.
   Table 5 presents results from a single node equipped with 8 NVIDIA H100
GPUs. Unlike the previous system, the H100 results are limited to intra-node scal-
ing (up to 8 ranks). The single-precision performance reaches 64.6 GLUPS at
8 ranks, with a speedup of 6.6 and efficiency of 0.82. Double-precision achieves
46.5 GLUPS at 8 ranks, with a speedup of 7.9 and efficiency of 0.99. These values
reflect the H100’s superior per-GPU performance compared to the A100, as it ena-
bles a 2.1× speedup over A100 at 8 ranks in double precision. On the other hand,
the decrease in single-precision efficiency at 8 ranks indicates the need for further
analysis and potential optimizations within TNL-LBM. However, the single-node
limitation prevents assessing multi-node scalability, as all communication occurs via
NVLink without inter-node InfiniBand transfers.

is apparent even in single-node computations on both A100 and H100 accelerators,
where all communication is accomplished through NVLink. However, this problem
is not due to the communication cost—the communication is completely overlapped
with computation, but the computation itself is slower than it should be. The size
of the CUDA thread block is (1, By , 1) for all lattice sizes used in this study, where
By = 256 for single precision and By = 128 for double precision. It can be seen that
the performance of the LBM algorithm is decreased in cases where Ny is not a mul-
tiple of By due to inactive threads compared to the optimal case where Ny is a multi-
ple of By.

7 Conclusions

The TNL-LBM project represents a robust and versatile implementation of the lat-
tice Boltzmann method (LBM), designed to address the challenges of large-scale,
high-fidelity simulations in computational fluid dynamics (CFD) and multiphys-
ics applications. By leveraging the Template Numerical Library (TNL), the frame-
work achieves a balance between modularity, performance, and scalability, enabling
researchers to tackle complex problems ranging from turbulent flow modeling to
fluid–structure interaction and coupled multiphysics systems. The modular architec-
ture of TNL-LBM allows seamless integration of diverse LBM variants, boundary
conditions, and collision operators, while its high-performance design ensures effi-
cient utilization of modern heterogeneous computing architectures, including multi-
core CPUs, GPUs, and distributed memory systems.
   The computational algorithm, formulated to support both single-node and distrib-
uted implementations, demonstrates strong scalability on the Karolina supercom-
puter and NVIDIA H100 GPUs. The benchmark results highlight the ability of the
framework to maintain high parallel efficiency even under challenging scaling sce-
narios, with double-precision computations showing superior scalability compared
to single precision due to more efficient utilization of the hardware. These findings
underscore the importance of code optimizations for data layout and communica-
tion, such as aligning memory access patterns and minimizing latency. While the
presented benchmarks include only results obtained on NVIDIA GPUs, note that
thanks to the performance portability layer provided by TNL the project also sup-
ports running simulations on the AMD platform via the ROCm/HIP toolkit. The
performance comparison of free and open-source LBM projects demonstrates com-
petitiveness and high performance of the TNL-LBM project.
   Beyond technical performance, the use of the MIT license further enhances the value
of the project to the scientific community, fostering reproducibility, collaboration, and
 167      Page 32 of 35                                                                         J. Klinkovský et al.


integration into proprietary workflows. This licensing choice, combined with demon-
strated computational scalability, lowers barriers to adoption and encourages collabora-
tion between academia and industry. The validation of the framework on a wide range
of problems, including non-Newtonian flows and coupled solvers, demonstrates its reli-
ability and adaptability to real-world engineering and scientific challenges. Future plans
for the project currently include integrating advanced collision models for compressible
flows, improving the implementation of the immersed boundary method for fluid–struc-
ture interaction, and utilizing advanced strategies for in situ/in-transit visualization.
    In summary, TNL-LBM provides a powerful and flexible tool for high-perfor-
mance LBM simulations that combine algorithmic innovation with modern software
engineering practices. Its success in scaling to 128 of GPU-accelerated ranks on
Karolina and achieving high performance on H100 systems highlights the project’s
capabilities in performing large-scale and high-fidelity simulations where accuracy
and efficiency are crucial factors.
